\section{Introdução}
A construção do Cbuild - Uma ferramenta de automatização para projetos em c - foi o foco desse trabalho, feito em script (Bash) com conceitos de versionamento de código, moduralização lógica através de funções e tratametnos de erros.

\section{Estrutura}

A ferramenta foi implementada em um único arquivo, com suas funcionalidades organizadas e encapsuladas em diferentes funções. Sua utilização é realizada por meio da linha de comando do Bash. O comportamento da ferramenta pode ser configurado por meio do arquivo \texttt{cbuild.conf}, que permite definir o diretório no qual o \texttt{cbuild} será executado, o compilador C utilizado na compilação dos arquivos-fonte, o nome do executável gerado e as \textit{flags} de compilação.

\section{Arquitetura}
A arquitetura do script é composta por três camadas principais:
\begin{enumerate}
    \item \textbf{Camada de Configuração (Flags)}
    \item \textbf{Camada de Módulos (Funções)}
    \item \textbf{Camada de Roteamento (Case)}
\end{enumerate}

Essa decisão de projeto nos ajudou no desenvolvimento, pois consegumos delegar cada camada para 1 ou 2 integrantes e trabalharmos separadamente em cada camada, onde um erro não interferia no desenvolvimento do outro sub-grupo.

\subsection{build}

O comando \texttt{build} constitui o núcleo do processo de compilação da
ferramenta. Antes de iniciar a compilação, a função realiza algumas
verificações e prepara a estrutura de diretórios necessária para a execução.

Inicialmente, verifica se o compilador definido pela variável \texttt{CC},
configurada no arquivo \texttt{cbuild.conf}, está disponível no sistema. Caso
o compilador não seja encontrado, uma mensagem de erro é exibida e a função
é encerrada com o código de retorno \texttt{2}.

Em seguida, a função verifica a existência dos diretórios utilizados para
armazenar os arquivos gerados durante o processo. Caso os diretórios
\texttt{build/} ou \texttt{logs/} não existam, eles são criados
automaticamente.

Por fim, é verificado se o projeto possui arquivos de código-fonte com
extensão \texttt{.c}. A ausência do diretório \texttt{src/} ou de arquivos
\texttt{.c} faz com que o processo seja interrompido, retornando o código
\texttt{3}. Dessa forma, antes de iniciar a compilação propriamente dita,
a ferramenta garante que o compilador esteja disponível, que os diretórios
necessários existam e que haja código-fonte a ser compilado.

\begin{itemize}
    \item \texttt{2}: \texttt{CC} não está instalado
    \item \texttt{3}: Não há arquivos de código-fonte válidos
\end{itemize}

A estratégia de descoberta de arquivos de forma recursiva  sobre todos os arquivos de origem. Cada arquivo \texttt{.c} é compilado individualmente para um arquivo objeto \texttt{.o} dentro do diretório \texttt{build/}.

\subsection{run}

A função \texttt{run} é responsável pela execução do projeto após a
compilação. Inicialmente, é criado ou atualizado o arquivo
\texttt{.last\_run}, localizado no diretório \texttt{build/}, com o objetivo
de registrar a última execução da ferramenta.

Em seguida, a função verifica se o diretório definido por
\texttt{BUILD\_DIR} existe e se o executável especificado pela variável
\texttt{TARGET} está presente nesse diretório. Caso alguma dessas condições
não seja satisfeita, a execução é interrompida, uma mensagem de erro é
exibida e a função retorna o código de erro \texttt{4}.

Quando as verificações são satisfeitas, o executável é iniciado e os
argumentos armazenados em \texttt{run\_args} são repassados a ele. Dessa
forma, é possível fornecer argumentos de linha de comando ao programa por
meio da opção \texttt{-r} do \texttt{cbuild}. Ao término da execução, a
função retorna o código \texttt{0}, indicando que o processo de execução foi
iniciado com sucesso.

\subsection{clean}

O comando \texttt{clean} é responsável pela remoção dos artefatos gerados
durante a compilação e pela limpeza dos arquivos de registro. Antes da
remoção, a função exibe os arquivos presentes nos diretórios
\texttt{build/} e \texttt{logs/}, permitindo visualizar os artefatos que
serão excluídos. Em seguida, esses arquivos são removidos por meio do
comando \texttt{rm -f}. A função retorna o código \texttt{0} após a
execução da operação.

\subsection{rebuild}

A função \texttt{rebuild} implementa o mecanismo de \textbf{compilação
incremental}, evitando a recompilação desnecessária de arquivos que não
foram modificados desde a última compilação. Inicialmente, são realizadas
as mesmas verificações preliminares do comando \texttt{build}: verifica-se
se o compilador definido pela variável \texttt{CC} está disponível no
sistema e se existem arquivos de código-fonte \texttt{.c} no projeto.
Também são criados, caso não existam, os diretórios \texttt{build/} e
\texttt{logs/}.

Em seguida, para cada arquivo-fonte, é determinado o nome correspondente
do arquivo objeto. A função utiliza o operador \texttt{-nt} do Bash para
comparar diretamente as datas de modificação dos arquivos. Caso o arquivo
fonte seja mais recente que o respectivo arquivo objeto, o código-fonte é
recompilado. A mesma situação ocorre quando o arquivo objeto ainda não
existe.

Durante o processo, a variável \texttt{changed} registra se algum arquivo
foi recompilado. Ao final, a etapa de linkagem do executável principal é
realizada somente quando pelo menos um arquivo-fonte tiver sido
recompilado. Caso nenhum arquivo tenha sido modificado desde a última
compilação, a etapa de linkagem é omitida.

A função retorna os códigos de erro \texttt{2} e \texttt{3}, utilizados
também pelo comando \texttt{build}, respectivamente quando o compilador
definido em \texttt{CC} não é encontrado ou quando não há arquivos de
código-fonte válidos no projeto.

\subsection{info}
O comando \texttt{info} coleta e exibe metadados vitais do projeto. A estratégia de contagem de arquivos e das Linhas de Código utiliza os comandos \texttt{find} acoplados ao utilário \texttt{wc -l}. O script processa de forma recursiva os diretórios \texttt{src/} e \texttt{include/}, lidando de forma segura com diretórios vazios. 

Além das estatísticas de código, a função obtém o tamanho em disco do executável utilizando \texttt{du -h} e extrai as datas da última compilação (via \textit{timestamp} do binário) e da última execução (através de um arquivo de controle gerado no momento do \texttt{run}). Todos esses dados são exibidos na saída padrão e exportados para um arquivo texto consolidado dentro da pasta \texttt{relatorios/}.

\section{Modos verbose e debug}

Para implementação dos modos de execução \textit{verbose} e \textit{debug}, utilizamos um loop com \texttt{getopts} para decidir quais métodos serão ativados com base nas flags passadas como argumento (\texttt{-D} para debug e \texttt{-V} para verbose).

\begin{verbatim}
verbose='false'
debug='false'
run_args=''
while getopts "VDr:" flag; do
    case $flag in
        V) verbose='true' ;;
        D) debug='true' ;;
        r) run_args="${OPTARG}" ;;
        *)
            echo "Opção inesperada ${flag}"
            exit
            ;;
    esac
done
\end{verbatim}

\subsection*{\texttt{verbose\_mode()}}

Função responsável por inicializar o modo verbose. Ela executa todo comando escrito depois dela dentro do script, até que \texttt{set +v} seja chamado.

\subsection*{\texttt{debug\_mode()}}

Função responsável por inicializar o modo debug. Ela executa todo comando chamado depois dela dentro da execução do script, não necessariamente escrito abaixo dela, até que \texttt{set +x} seja chamado.

\subsection*{\texttt{end\_mode()}}

Função responsável por encerrar os modos debug e verbose.

A cada chamada dos comandos principais \texttt{build}, \texttt{rebuild}, \texttt{clean}, \texttt{run} e \texttt{info}, colocamos um condicional que, com base na verificação das flags feita anteriormente, executa esse comando em modo verbose.

Logo antes da parte do código que decide quais comandos serão executados com base nos argumentos passados na execução, inicializamos o modo verbose para execução desse trecho do código. Também inicializamos o modo debug nessa parte para que tudo que seja chamado posteriormente seja executado em modo debug.

Logo após cada comando, chamamos a função que encerra os modos debug e verbose, para evitar que outros comandos não chamados sejam executados em modo verbose.

\section{Geração de logs}

\subsection*{Função \texttt{gerar\_logs()}}

Cria um arquivo de log da última execução do script, contendo as seguintes informações:

\begin{itemize}
    \item Data/horário de execução;
    \item Código de retorno;
    \item Saída do comando executado;
    \item Comando executado;
    \item Tempo de execução;
    \item Status da execução.
\end{itemize}

\subsection*{Pontos importantes sobre as decisões de projeto}

A variável padrão \texttt{BASH\_XTRACEFD} diz para qual descritor será direcionada a saída de \texttt{set -x}.

Com o comando \texttt{exec}, podemos redirecionar a saída do descritor criado 3 diretamente para a saída 2 (\texttt{stderr}) do terminal. Sem o descritor 3 redirecionado para \texttt{\&2}, o rastro de \texttt{set -x}, com descritor padrão \texttt{stderr} (descritor 2), seria direcionado para o log na execução do comando com o \texttt{tee}. Isso faria com que tudo o que fosse impresso no modo debug aparecesse na saída do nosso comando dentro do log. Para evitar isso, direcionamos a saída do \texttt{set -x} para o descritor 3, que por sua vez redireciona essa saída diretamente para o \texttt{stderr} do próprio terminal, fazendo com que a saída do \texttt{set -x} apareça apenas no terminal e não no log.

\begin{verbatim}
exec 3>&2
BASH_XTRACEFD=3
\end{verbatim}

\begin{verbatim}
exec 3>&-
\end{verbatim}

Encerra o descritor 3, pois ele não será mais usado.

\begin{verbatim}
"$comando_exec" 2>&1 | tee -a "temp_log.txt"
\end{verbatim}

Executa o comando \texttt{comando\_exec} e redireciona sua saída para dois canais: um para a saída padrão no terminal e outro para o arquivo \texttt{temp\_log.txt}.

\begin{verbatim}
inicio=$(date +%s.%N)
fim=$(date +%s.%N)
\end{verbatim}

Para calcular o tempo de execução, tiramos a diferença entre o horário de início e o horário de fim da execução, calculando assim o tempo total de execução.

\begin{verbatim}
tempo_real=$(echo "$fim - $inicio" | bc)
\end{verbatim}

Para números menores que 0.5, o \texttt{bc} pode retorná-los sem o 0 da primeira posição; por isso, tratamos esse caso:

\begin{verbatim}
if [[ "$tempo_real" == .* ]]; then
  tempo_real="0$tempo_real"
fi
\end{verbatim}

\begin{verbatim}
LC_NUMERIC=C printf -v tempo_real "%.4f" "$tempo_real"
\end{verbatim}

Para salvar o tempo com um certo formato, é preciso tratar a representação de números decimais, trocando a vírgula por um ponto como separador decimal. Isso é importante pois o \texttt{printf} pode apresentar erros caso o número decimal use vírgula na formatação \texttt{\%.4f}.

\begin{verbatim}
rm -f "temp_log.txt"
\end{verbatim}

O arquivo temporário usado para salvar a saída do comando é excluído após seu uso.

\section{Dificuldades Encontradas}
Durante o desenvolvimento, algumas dificuldades técnicas apareceram. tivemos algumas dificuldades com o escopo de variáveis no Bash, especialmente quando se trata de caminhos de diretórios entre funções. Além disso,  a implementação correta da compilação incremental, que demandou testes cuidadosos para garantir que as comparações ocorressem sem falhas mesmo quando os arquivos objetos ainda não haviam sido criados no primeiro \texttt{build}.

\section{Resultados Obtidos}
O \texttt{cbuild} foi capaz de realizar todos os requesitos do trabalho. A estrutura em camadas foi extremamente últil para a organização e versionamento do projeto.

\section{Melhorias Futuras}
para melhor vizualação do usuário, seria de extrema importância os seguintes incrementos:
\begin{itemize}
    \item \textbf{Suporte a múltiplas linguagens:} Expandir a descoberta de arquivos para compilar também arquivos \texttt{.cpp} (C++), automatizando a troca entre \texttt{gcc} e \texttt{g++}.
    \item \textbf{Cores no Terminal:} Adicionar códigos ANSI no sistema de *logs* e \textit{stdout} para diferenciar visualmente avisos, mensagens de sucesso e erros críticos.
\end{itemize}
